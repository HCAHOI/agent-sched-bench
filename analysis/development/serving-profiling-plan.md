# 覆盖 mixed56 的 PPD Profiling 计划

## 1. 这次要做什么

在相同模型、GPU与serving配置上，对“历史长度、新增输入长度、输出长度”的真实组合分别测PD与D本地处理，得到PPD可以使用的新性能数据。然后检验新数据是否改变PPD决策，以及能否改善相同mixed56上的表现。

先做约一小时初步profiling，再完成全部声明范围。一小时不是完整工作的截止时间。用户已于2026-09-08批准开始实施与运行；先核对初步结果和完整耗时，再继续完整阶段。旧32K及后续context/state队列已停止，已有输出已保留并拉回。

本计划只围绕长度覆盖和PPD调优，不开发新的实时缓存/负载调度器。

## 2. 取点数据与规则

数据来自已经完成的 `results/mixed56-vast-ppd-pcie-20260907-r1/server/routing.jsonl`，使用56个原始任务的2414个后续请求，排除replacement。相同原任务、相同轮次的两个replica归为一组，固定取replica-001，得到1207个去重请求。复制样本不当作独立证据；56任务运行仍用于最终正式验证。

先按以下范围分格子，边界在测量前固定：

| 维度 | 分格范围（tokens） |
|---|---|
| 历史H | ≤4096；4097–16384；16385–32768；32769–65536；>65536 |
| 新增输入U | <512；512–2048；>2048 |
| 输出O | ≤128；129–512；>512 |

理论上有5×3×3=45格，实际41格有请求。每个非空格取一个真实请求：先算格内H/U/O各自log2值的中位数，再选离这三个中位数的绝对距离之和最小者；并列按job_id、turn排序。取点只看长度，不看方法输赢或请求耗时。

这得到41个代表点。再补H/U/O各自最小和最大的真实请求，去重后新增6点，共47点。极值来自真实组合，不把107K历史、5.5K输入和1.3K输出的三个独立最大值拼成不存在的请求。

最后加9个输出长度对照：从三个真实代表点固定H/U，仅把O改成32、256、1536。它们用于看输出变长是否改变两种处理路径的得失，明确是受控对照，不声称这些9个组合都有真实出现频数。

完整清单因此是 **47个真实长度点＋9个输出对照＝56个长度点**。一个代表点代表一个分布格子，不意味着整个格子内所有长度的性能相同。报告每格请求数、实测长度及邻近查询误差；不能用“41格全覆盖”冒充全部系统状态都覆盖。

## 4. 每个点具体怎样测

使用现有2×L40S、Qwen3-4B FP8、vLLM0.28.0和native NixlPushConnector。保留max_num_seqs=8、batched_tokens=2048、chunked prefill、prefix cache、eager及现有GPU内存配置。模型加载一次，点之间释放会话、等待传输/请求结束并重置prefix cache，避免按点重启整个模型。

每个“长度点＋到达档位＋处理路径＋重复”是一个测量组：

1. 创建8个独立两轮会话，用不同且可复现的prefix避免会话之间意外共享缓存。
2. 第一轮统一走PD，真实生成32个token；调整第一轮输入使第二轮开始时历史达到该点H。这32个token仅用于建立上下文，不计入第二轮性能，但其计算时间计入实验预算。
3. 第一轮结束后立即提交第二轮，新增U个token，完整生成O个token。PD组在P上prefill再传D；本地组在D上处理第二轮。两条路径都不运行PPD自动决策，先测动作本身。
4. 两条路径使用相同输入构造、会话到达序列、生成参数与输出长度。两轮链接保留各自真实生成结果；因此核对每条请求的实际token长度、prefix匹配量和缓存命中，不能假定不同路径生成的文字完全相同。
5. 八个会话全部完成后才清理并开始下一组。新会话数是固定8个，不再按QPS×十秒不断扩大请求数；没有replacement流，也没有正式mixed56的任务并发32。这里只测受控长度场景，正式mixed56验证保留原并发、tool sleep/4和replacement协议。

H/U使用现有tokenizer和聊天模板的实际token数定义。用公开PPD的多样化文本生成器构造输入，再裁剪/补齐使第一轮prompt精确为H−32；第一轮真实生成32个token后，按真实输出与重新套用的聊天模板核对共同前缀。GPU采样前固定容差：实际H允许±8 tokens但不得跨历史分格，实际U必须精确，实际O必须完整；否则该组失败并诊断。skip_special_tokens=false用于保留真实生成特殊token，输入与输出原文/token ID均保存。所有路径保留实际H/U，不以改写标签消除差异。

八个长历史会话可能超过同时驻留的KV容量，由原生引擎处理；记录真实命中、排队和抢占，不声称每个请求都暖缓存。这是该固定两轮协议的测量条件，不把它解释为mixed56缓存存活率复现，也不新增人为缓存丢失矩阵。

## 5. 只用两个已有PPD负载档位

旧mixed56中，需查表的1452个后续请求有1178个选0.5档、274个选1档；没有使用2至20档。因此本轮只测公开PPD profiling的0.5和1这两个会话到达参数，不扫其余八档。

这两个数字是公开benchmark的会话到达速率标签，PPD在线查询使用的是累计LLM请求速率；一会话有两轮，二者不能当作相同的物理QPS。沿用公开到达生成器并固定每组8个会话，保存T1/T2实际到达时间及实际LLM速率。接入新表前必须核对这个速率映射；不能仅因数字同为0.5/1就声称压力与mixed56一致。若映射使已有范围缺测，先列出实际缺口与额外成本，不能直接启动另一轮大扫描。

每个长度点在两个会话到达档位分别测PD和本地路径。每种组合独立重复两次，种子42与43；种子内两路径共享到达序列和输入构造，第一次PD→本地，第二次本地→PD。两次用于观察重复噪声，不是把每个token当独立样本，也不足以声称稳定P99。

## 6. 每个点保存与比较什么

| 指标 | 具体含义／用途 |
|---|---|
| 第二轮TTFT | 提交第二轮到第一个输出token的时间，看哪条路径更快开始回答 |
| 第二轮decode TPOT | (最后token时间−第一token时间)/(O−1)，看完整生成期间每token平均耗时；不含prefill |
| 第二轮E2E | 提交到第二轮完整结束，看首token收益是否被后续生成变慢抵消 |
| 引擎排队/prefill/decode span | 区分时间花在哪个阶段；span不是纯GPU计算时间 |
| 实际H/U/O、命中token、KV传输字节/耗时 | 验证长度与完成情况，解释prefill/transfer成本 |
| 组完成时间、完成率及全部失败 | 防止只比较成功请求，隐藏超时或未完成 |
| 第一轮建立历史的耗时 | 解释profiling本身为什么耗时，并纳入完整预算 |

输出32、256、1536都必须真实生成到指定长度（ignore_eos并核对completion_tokens）。不能用一个token、固定64步或缩短输出替代长输出测量。既保留客户端token流时间，也保留现有引擎阶段记录；客户端SSE若合并token，TPOT只解释为整段平均，不声称逐token GPU时间。

失败/超时保留实际已完成token和观测时长，不赋假完成时间。初步沿用单请求1800秒截止；任一请求超时，该组停止并保留已完成与取消的明细。完整阶段的单请求截止根据初步测得的历史构建、指定输出生成和排队时间固定，且不超过代理的1800秒截止；发生超时先诊断而非继续扫一串只产超时的点。不同路径的截止规则一致；不把失败路径剔除后算看似更好的分数。

原始结果按(H,U,O,会话到达参数,路径,重复)保存，不强塞回旧的9个PPD类别。各格请求数只用于描述工作负载权重，极值点和受控对照单独报告，不提高其总体权重。

## 7. 初步与完整阶段的确切工作量

第一阶段优先按P02→P43→P45→P47→P54→P55→P56执行：分别检查短历史普通输出、最长历史、最大新增输入、最长真实输出，以及固定长历史/较长输入时的32/256/1536输出对照。先用0.5档、种子42，对每点测两条路径。

这7点是14个测量组，共112个第二轮请求和112个建立历史请求。第二轮共56784个生成token，第一轮共3584个；不能承诺所有点一定在一小时完成。约一小时检查进度与分类耗时，在途组正常收尾；未完成的点仍在总清单里，不因检查点到时删掉。

初步阶段核对长度构造、完整输出、指标与会话/请求速率映射，并给出完整版的时间和费用估计。测量程序完成14组后保留引擎运行，等待协调者记录实测耗时核对后继续；这一检查不要求用户重复批准已授权范围。不同历史/输出档位分别估时，不能用短点时间乘所有点。符合完整协议的已测组直接复用。

完整阶段：56长度点×2会话到达档位×2路径×2重复＝448个测量组。每组8个两轮会话，即3584个第二轮请求和3584个历史建立请求。第二轮共1191936个指定输出token，历史建立共114688个，合计1306624个生成token。这是真实完整工作量，尚未包含失败重跑；不是一小时初步阶段的工作量。

剩余时间按初步各类组的实测耗时乘尚未执行组数，加模型启动、清理、验证和结果打包；费用为实例费率×实耗小时。完整版可以超过一小时，启动前明确预计时间/费用。异常或明显超预计时诊断；不默默删点、降输出或少跑某条路径。

## 8. 数据怎么用于PPD，怎样判断任务完成

先检查新数据是否能被PPD查询实际使用：历史、新增输入、在线预测输出必须映射到新测量范围，不能所有长历史仍落回原large/huge_paste。PPD评分公式沿用公开TTFT改善与TPOT代价的权重；新表的长度映射及缺测处理在读取新mixed56性能前固定并审查，不在本轮顺便开发新的缓存/负载决策规则。

公开PPD的<512 bypass仍会跳过表。短输入照样profile，明确区分“测出了差异”和“现有规则会采用差异”；若要调bypass阈值，必须单独列明这个公开参数变化及其依据。在线预测不能偷看本次请求的真实输出长度，profiling指定O只属于实验控制。

再用完整、相同配置的mixed56验证新表支持的PPD，与已有原PD/原PPD比较任务完成时间、makespan、TTFT、decode TPOT和全部失败，并分别看长短历史、新增输入<512/>=512、长短输出的结果。只有正式验证才能说明PPD是否改善；两轮profiling不能代表完整agent运行。

mixed56已被分析，属于开发场景。取点可以依据其长度分布，但不把改善包装为未见工作负载上的泛化。无法改善也是结果，需要明确是测量覆盖、速率/长度查表映射、bypass或实际动作收益中的哪一环没有带来收益。

完成交付包括56点的完整测量与失败明细、PPD实际消费新表的核对、相同mixed56正式比较。不能以一小时初步数据替代完整交付。
