为什么 state 没有作用

Observed：四个目标上都是 0 PMF difference。

semantic-only 与 semantic+state 不只是 accuracy 相同，而是 119 个 pip command 的全部预测分布都相同；resource probability 也全部相同。

  • 11 个 “pip 不存在” 通常在第一次 install 执行后才知道 absent；预测当前 command 时还不可见。
  • 只有 15 个 command 实际启用了 non-exact semantic evidence，状态条件化没有改变其 evidence set。
  • 5 个 apt && pip command 在 apt 失败后没有执行 pip clause；它们仍是 command-level pip queries，但不能产生 pip observation。

Inference：现有 task 内缺少“先建立状态，再重复一个 non-exact pip query”的序列；不是状态理论上无用，而是这 100 条 trace 没提供可利用的 state contrast。

结论与下一步

证据支持

  • 针对常见 tool 的 deterministic semantic parser 值得做：pip package-set matching 在 latency 与 Disk 上各有小的净收益。
  • 统一 KB 不必理解 dependency resolution；parser 只负责产生语义 key，预测仍由同一个因果 episodic memory 完成。
  • CPU/RSS 的 pip 子集极端偏 Light，accuracy 已被 majority ceiling 卡住；这里不是继续调权重的好目标。

不要过度声称

  • state arm 没有任何边际收益，不能讲“task-container state 解决了 cache/availability”。
  • Latency +3 与 Disk +2 都很小；没有 fresh repository 证据。
  • 下一步应先做一个新的 tool parser（例如 pytest/apt）或在 fresh repo 上冻结确认；不要在 SQLGlot100 上继续调 alpha、flags 或 package-specific rules。

最窄且站得住的 story：generic argv matching 失败后，tool-specific semantic key 能修正少量 pip 决策；更丰富的状态只有在 trace 真正包含可复用的 state contrast 时才可能有用。
